查询增强：用户不一定会说“幂等”

用户问“为什么同一个通知来了两次，不能再发一次货”，文档写“回调幂等”。这类失败发生在表达对齐阶段。文档已经存在，也没有解析错误，但查询和片段未落到同一个检索入口。

改写要保留业务限定

可以将问题改成“支付回调重复投递时，幂等和发货去重如何处理”。这让检索器看到领域词，但原问题仍然是回答目标。若用户问测试环境，不应改成生产环境；若用户问“为什么不能”，也不能改成“如何绕过”。

实际流程可以保留原查询与改写查询两路结果，再按片段 ID 合并。日志记录原文、改写、被触发的检索路线，才能分清改写帮助了匹配，还是把问题改成更容易答的另一个问题。

原文若包含商户信息或内部编号，发送到外部改写模型前也需要数据策略。不能因为这一步还没生成答案，就忽略外传风险。

复杂问题可以拆，但要留住连接关系

“退款失败为什么不能直接再发起？该找谁处理？”可以拆成退款失败规则和模块负责人两个子问题。第二个问题可能要先查模块归属，再查团队职责，不能提前假定负责人就是检索结果中出现次数最多的人。

拆解后按子问题检查证据，避免第一个问题返回很多相关材料，掩盖第二个问题一条也没有。查询数、每路 top-k 和总等待时间应设上限，否则一句用户问题可能扩散成很多外部调用。

Step-back 则将具体问题暂时上提为更一般背景，比如先了解“异步通知的一致性风险”。它适合补充解释，却不能替代当前规范的精确条件。

HyDE 在查询时生成假设文档

HyDE 先让语言模型写一段可能回答问题的文档，再为这段假设文本生成向量，检索真实资料。它利用文档式表达接近文档集合的表示，假设文本中可能包含错误细节。

用户问题 → 假设文档 → 文档向量检索 → 真实原文 → 证据包
                 不直接作为事实依据 ↗

这里最重要的边界是：假设文档只提供检索线索。假设里写了“按订单号去重”，真实规范写“渠道流水号加事件类型”，最终回答应以真实规范为依据，不能把假设答案混进证据包。

上游 README 有将 HyDE 描述为假设问题的表述，但对应 Notebook 和原论文都以生成假设文档为关键步骤。本书据此区分，不沿用容易混淆的名称。

HyPE 把生成问题提前到入库

HyPE 在索引时为每个片段生成若干可能的问题，用这些问题的向量作代理。用户的问题命中代理后，返回原片段。因此是问题与问题之间的匹配，再回到原文。

假设每块生成 5 个问题，索引向量数也可能明显增加。它没有查询时生成假设文档的那次 LLM 开销，但仍然需要查询 embedding、检索和回答，不是“查询完全没有成本”。文档更新后，问题代理也需要重建。

代理应保存父片段 ID，多个代理命中同一片段时去重。不能把“可能被问的问题”当成文档已经回答的事实。Document Augmentation 与 HyPE 都利用问题增强，索引组织和回映射方式应按具体实现核对。

这个阶段怎么选

如果只差几个固定术语，先试受控同义词表或原查询加改写。问题结构复杂时试拆解。短问题与长段落表示不对齐时，再比较 HyDE；查询量很大、文档相对稳定时，可以评估把开销前移的 HyPE。每次保留同一批独立题目对照。
