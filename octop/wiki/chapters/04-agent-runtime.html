第 04 章

Agent 装配：配置如何变成能力

源码快照 2026-10-27 · 约 8 分钟

Agent 行不是 Agent 对象#

控制面中的 Agent 行记录身份、归属、启用状态、模型选择与配置。真正执行模型循环的是通过 octop-harness 创建的运行对象。两者之间由 Octop 的 AgentManager 负责转换。

林岚把研究专家的默认模型改了，首先改变的是持久配置。正在执行的任务是否立即改变、下一轮是否使用新模型、是否需要重建运行时，是另外三个问题。把“配置保存成功”等同于“所有活跃对象已更新”会产生难以解释的故障。

当前 manager.py 很大，既管生命周期，也负责模型、工具、策略与工作区装配。阅读时应沿一个方法的输入输出走，不必从第一行读到最后一行才建立结构。

装配出一份 HarnessAgentConfig#

_build_harness_config 附近是理解能力来源的关键。它把若干独立来源合到 HarnessAgentConfig：

来源 装配结果 需要留意
Agent 行与 config_json 名称、提示、默认模型、能力开关 存储表示不等于生效表示
后端解析 workspace_dir、backend 文件内容与执行环境分开
Provider 解析 具体模型引用与候选 自动选择与显式选择不同
Connector / Plugin / Skill 工具、MCP 配置、技能目录 只有启用且有效的能力应进入
安全配置 SecurityPolicy、interrupt_on Agent 覆盖不应绕过全局约束
Memory 配置 后端与辅助抽取模型 与聊天模型未必相同

源码还根据 HarnessAgentConfig 可用字段进行兼容处理。这提醒我们：宿主与运行库各自发布，安装依赖满足版本下限并不等于所有可选行为都完全相同。分析宿主代码时不能默认最新库内部契约永远不变。

中间件不是任意排序的清单#

宿主装入配额、reasoning、知识搜索提示、浏览器 profile、二进制读取保护、图片材料化、线程产物记录和 octop_ui 大载荷卸载等中间件。外层还有按条件加入的模型重试或安全 failover。

顺序会改变谁看到原始内容、谁看到精简内容。源码注释明确要求 OctopUiOffload 保持在特定内层，使其他中间件观察到一致的瘦身结果。它针对插件 octop_ui envelope，不应被泛化为“所有工具输出统一压缩”。

以访谈附件为例，工作区图片路径需要在模型调用前变成模型可读的内容；文件生成以后，又要把路径关联到当前线程。一个处理输入材料，一个记录输出产物，虽然都涉及文件，却不该合成一个万能文件中间件。

并发有不止一种锁#

manager.py 中可以定位按 Agent 的生命周期锁、按 Agent 与 thread 的执行锁、在途调用计数及维护相关保护。它们解决的冲突不同。

研究专家配置重载时，不应同时被另一路启动或停止；同一线程的流式调用与 HITL 恢复也不应任意交叉写状态。记忆精简或恢复则涉及存储维护，不能在仍有写入时随意替换文件。

这些锁是本进程的协调工具，不是跨实例锁。即使两个进程用了相同 agent_id，它们也不会共享 Python 的 asyncio.Lock。

重载并非唯一更新方式#

部分变更需要重建运行时，例如某些 Provider 或插件配置；部分启用禁用可热同步，例如技能过滤集合。源码还有“等待中的图刷新”与有界并发重载逻辑。

由此可以得到一个维护原则：每个配置写入接口，都应明确它是仅持久化、原地更新还是重建。若 API 已返回成功而更新在后台执行，界面还需要能表达实际状态与失败信息。

一个适合重构但不必立即重构的切口

若需要降低 manager.py 的认知负担，可以先把“将已解析输入生成配置”的部分提取成可测试步骤，保留生命周期所有权。这里是演进建议，不是认定文件超过某个行数就必须拆服务。先增加配置组合的契约测试，比引入一个远程装配服务更直接。

动手检查#

林岚禁用了某个 Skill，又替换了模型供应商。为什么不能让两个操作统一执行“更新数据库后什么都不做”？

答案提示： 运行对象可能仍持有旧过滤集合、旧模型 factory 或旧工具绑定。需要按变更类别热同步或重建，并明确在途任务使用哪个配置快照。数据库记录正确只是必要条件。
