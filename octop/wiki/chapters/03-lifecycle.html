第 03 章

启动与退出：谁把系统装起来

源码快照 2026-10-27 · 约 8 分钟

两个装配入口，各有职责#

启动命令最终进入 launch.py 的 run_foreground。这里同时知道 OctopServer 与 FastAPI，并把它们接给 uvicorn。业务组件的装配放在 infra/server.py，HTTP 应用组装放在 api/app.py。

这样的边界防止业务核心为了启动渠道而反向依赖 HTTP 路由，也让嵌入式 CLI 可以使用 OctopServer 而不必总启动 Web 服务。所谓 composition root，就是集中决定“创建谁、把谁传给谁”的位置，不是一个新的业务服务。

从文件到可接收请求的系统#

常规路径可以压缩成下面的依赖顺序：

PathLayout 与配置
  → 专家 / 子 Agent 目录，插件播种与加载
  → 打开控制面数据库，执行迁移
  → SharedServices 与 JWT 所需材料
  → AgentManager、历史/轨迹服务、Gateway、Cron 等
  → AppRuntime
  → FastAPI 应用与监听器

这是一张依赖地图，不是源码所有语句的逐行列表。启动还包含日志、资源限制、浏览器配置、知识库任务恢复、Bridge 自动重连等支线。

源码提供一个容易漏掉的分支：首次安装时，数据库后端尚未由设置向导选定，should_defer_control_plane_db 可以让服务暂缓打开控制面。此时“进程活着”不等于“所有业务依赖已就绪”。bind_control_plane 在用户完成选择后再创建仓储和运行时。

林岚第一次打开页面看见向导，并不意味着服务启动失败。它进入了一个有意设计的未绑定状态。

配置不是读一次就结束#

配置来源包括文件与环境变量，Agent 和 Provider 的有效配置又来自控制面。设置向导换库还有空库条件下的重绑定路径。运行时组件因此提供 replace_* 或类似的更新接口，而不是让数据库模块随意修改其他对象的私有字段。

这个安排限定了切换时机，以及切换后必须保持一致的引用，并不支持任意热切换。ADR 002 把已有用户的运行环境与空库 setup 区分开；分段历史归档又会加上额外限制。不能把管理界面上有个数据库选项理解成随时在线迁移所有状态。

启动失败要区分层次#

模型未配置、某个 Agent 的远程后端失联、数据库迁移失败，影响范围不同。数据库连接与迁移是许多业务的基础；单个 Agent 的构建则可以有自己的失败状态和超时约束。AgentManager 中可以找到启动超时与有界重载相关代码。

对工作室来说，研究专家暂时不可用不应被误报成全部历史丢失。故障页面和日志至少要分清：宿主未就绪、用户未初始化、专家未运行、当次模型请求失败。

本书没有运行这些失败实验，这里给出的是根据装配依赖推导的排障顺序。

退出不是直接杀进程#

server.stop 会依次处理主动关怀调度、cron、gateway、Agent 注册表与用户侧资源，并关闭历史存储与数据库。退出过程中还涉及连接器会话和后端浏览会话的清理。

为什么先停调度再关 Agent？因为调度器继续派活时，运行资源可能已开始销毁。正确的退出过程需要停止接纳、处理或终止在途工作、刷新持久化、释放连接。源码的关闭序列提供了基础，但不要由此推定它对所有外部副作用提供了精确一次保证。

在纸上画启动状态机

可用未启动、已启动但数据库未绑定、数据库已绑定、业务运行中、关闭中、已关闭六个状态分析。它是教学抽象，不是源码枚举。为每条边标注触发者与失败时仍有效的资源，能很快发现“只判断进程是否存活”的健康检查遗漏。

动手检查#

首次设置选择 PostgreSQL 时连接失败，能否先创建管理员，再把用户表搬过去？

答案提示： 不应跳过目标数据库成功绑定这个前提。否则管理员写到哪一个控制面、后续 JWT 与仓储读哪一个控制面都会变得含糊。应按向导约束解决连接，再完成初始化，而不是临时发明迁移步骤。
