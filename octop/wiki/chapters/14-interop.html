跨端协作：ACP 与 Bridge 各管什么

源码快照 2026-10-27 · 约 8 分钟

都叫协作，执行位置不同#

工作室有两种新需求：编辑想在 IDE 里使用 Octop；另一个办公室有独立 Octop，想借用它的研究专家。前者是客户端/Agent 协议集成，后者是实例间桥接。

能力 对端是什么 执行位置
入站 ACP IDE 或终端客户端 本地独立 OctopServer 进程
出站 ACP 外部编程 Agent runner 外部 runner 所在宿主环境
Bridge 另一台 Octop 专家所在的远端实例

不要把“远端专家”自动塞进本机 Agent 注册表，也不要把 ACP 当成 Octop 的 HTTP 聊天 API。

ACP 是双向的 stdio 集成#

docs/acp.md 说明两种方向均使用 stdio JSON-RPC。入站 octop acp 作为 server，供 Zed 等客户端驱动；出站 acp_runner 作为 client，把任务交给外部工具。

入站命令会启动 standalone OctopServer，并非一定连接已经运行的 octop run。这对运维很重要：若多个进程指向相同数据目录，不能默认它们会共享内存中的锁和调度所有权。

出站 runner 配置是按用户共享，启用工具则按 Agent 控制。命令在运行 Octop 的机器上找 PATH、凭证和工作目录，不是在浏览器机器上执行。给浏览器安装一个 CLI，不能使远端服务突然找到它。

外部 runner 的 permission_required 还需要选择精确 option。不能把内部 HITL 的“批准”直接泛化为外部协议任何选项都已同意。

Bridge 不复制专家#

远程专家在本地用 bridge:{connection_id}:{remote_agent_id} 表示。浏览器仍请求本机 API，本机识别远端引用后转发；专家运行、线程权威、附件落盘与历史保留在专家所在侧。

浏览器
  → 本机 HTTP / chat WS
  → Bridge 连接：HTTP 隧道与 turn 流
  → 远端 API / GlobalProcessor / harness
  → 远端工作区与历史
  ← 响应、chunk 与按需历史

本机可以持有连接配置与临时状态，但不因此成为远端对话历史的第二个完整权威。桥断了以后，不应自动启动一个本地同名专家并续写，那会改变数据和工具归属。

两种 WebSocket 不要混#

Dashboard 的 WebSocketHub 服务浏览器到本机的订阅；Bridge 有独立的机机长连接，承载隧道与流式多路复用。浏览器不应直接改成访问远端 baseURL，以绕过本机桥接。

通用 HTTP 隧道可承载 method、path、headers、body 等，但产品安全策略不必允许所有路径。实际 tunnel_policy.py 对专家面、只读 composer、浏览器 viewer 等分别约束，未知路径默认拒绝。

docs/bridge.md 的某些模块清单仍是早期规划，当前实际文件包括 manager.py、transport.py、http_tunnel.py、peer_auth.py 和 peer_turn.py。书中的源码导航使用实际文件，不把规划文件名写成已实现。

同样的用户编号不是同一身份#

假设本机林岚是 user 7，远端合作账号是 user 12。隧道在对端用对应登录态执行，资源可见性应由对端用户决定。本机 user_id 不能直接复制成远端 user_id。

共享桥链接的使用者与连接所有者也有不同管理能力。评审要看路径、方法、连接归属及最终授权组合，而不是只判断连接是否已加密。

如果需要防止重复外发，还要跨桥保留动作身份和结果查询机制。Bridge 传输成功不等于工具事务成功；网络超时也不说明远端没有执行。

当前实现与生产承诺

官方 Bridge 文档仍标注“实现中”。本书只依据快照解释已可定位的结构，没有做跨实例联调、断网压测、版本兼容或安全验收。它适合研究边界，不应直接充当生产可靠性证明。

动手检查#

本机和远端各有一位叫 research 的专家。桥连接断开后，自动切成本机 research 是否是透明容灾？

答案提示： 不是。工作区、凭证、知识、记忆、线程和执行环境都可能不同。除非产品定义并实现了可验证的复制与故障转移协议，否则这是换了执行主体。
