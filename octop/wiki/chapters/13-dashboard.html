前端架构：流式对话是一台状态机

源码快照 2026-10-27 · 约 10 分钟

页面不是一份 messages 数组#

浏览器要同时表达正文增量、思考、工具调用、工具结果、附件、配额、审批暂停、错误、取消和多人说话。简单“收到 token 就拼字符串，收到 done 就解锁”无法覆盖这些状态。

Dashboard 使用 React、TypeScript、Vite、Ant Design 等组件。理解聊天架构的关键不是组件树有多少层，而是流状态由谁持有、消息怎样归属、历史如何与实时数据合并。

为什么 chatStore 放在组件之外#

chatStore.ts 文件开头说明：WebSocket 与累计消息置于模块级 store，在 React 组件卸载、重挂载后仍存在；组件通过快照订阅更新。

这解决一个具体问题：林岚切到设置页，聊天组件卸载，不应让在途任务的客户端状态立即丢失。回到聊天时可接上最新快照。

这里“持久”仅相对于页面组件生命周期，不等于浏览器关闭或服务端重启后的持久存储。真正刷新需要结合服务端历史和 turn_active 等状态恢复。不要把内存 store 的名称解释成磁盘数据库。

消息属于线程，也属于说话人#

parseHarnessChunk 将服务端帧转换为前端可理解事件。frameThread 等逻辑判断帧属于哪个线程；团队流还要依据 agent 标记和说话人规则合并气泡。

如果研究成员的 token 到来时，前端把它接到主持人的最后一条气泡里，文字可能完全正确，身份仍是错误的。若又把成员 done 当作整个房间结束，主持人总结尚未出现，输入框就可能进入错误状态。

所以“一个 WS 连接”不等于“一位说话人”或“一轮唯一完成事件”。同房间多任务是前端状态机复杂度的重要来源。

四个恢复判断各有用途#

wsResumeGate.ts 明确把弱恢复与滚动/历史交互分开。当前默认最多自动重新订阅 8 次，无 socket 的陈旧流宽限为 20 秒。这是产品启发式，不是网络可用性 SLA。

它还规定：是否探测活动任务，依据本地流状态或服务端 turn_active，而不是从最后一条消息长得像不像“没说完”猜测。长工具调用可能很久没有 token，socket 仍开着，不应只因沉默就强制封口。

后台未聚焦线程也有不同恢复策略，避免大量标签同时重连。一个等待图标看似简单，背后实际包含活跃状态、连接状态与用户焦点三条维度。

历史回填会与实时增量竞争#

假设历史接口刚开始读取时包含 20 条消息，网络返回前又收到新的流式内容。若直接 setMessages(history)，就可能覆盖这段新文本。

相反，如果把历史和当前列表无条件拼接，又可能重复展示同一条工具结果。正确做法需要稳定身份、去重、边界或明确的刷新约束。chatStore 中的历史、绘制、团队流、pending alias 与错误测试，正是在约束这些具体情形。

v2 分页要求原样携带 next_cursor，不能根据新消息数量变化用 offset 自行换算。前端分页协议属于历史一致性设计，不是纯 UI 实现细节。

测试要抓事件顺序#

一个有价值的前端测试不是只断言“渲染了某段文字”，而是依次注入 token、tool_call、断线、恢复、tool_result、done，再检查归属、状态和结果。

也可以测试：审批暂停时刷新历史、成员结束但主持人未结束、历史读取失败但旧内容还在、取消以后收到迟到帧。事件顺序一换，最终静态截图相同，也可能隐藏状态错误。

这些测试可以离线控制输入，不能替代真实浏览器与后端的联调。本书没有执行 Octop Dashboard 的完整测试。

从文件名回到事实

sseHelpers.ts 这样的历史命名仍被聊天 store 使用，但普通聊天连接实际由 WebSocket 构造。读代码时看连接创建、订阅及帧处理，不因 helper 名称就把主流程写成 SSE。

动手检查#

有人建议“20 秒没有 token 就结束加载，防止界面卡住”。为什么这会误伤正常任务？

答案提示： 可能正在等待工具、思考或审批。需要结合 socket、服务端 turn 状态和恢复策略；宽限逻辑不能把活连接上的安静任务直接视为完成，更不能把超时封口记成业务成功。
