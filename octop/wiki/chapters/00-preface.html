前言：沿一次任务读懂平台

源码快照 2026-10-27 · 约 8 分钟

从一个能核对的任务开始#

一家小型出版工作室希望把作者访谈整理成选题材料。编辑林岚在浏览器里提出：“查阅访谈附件和选题规范，请研究专家整理背景，再给我一份可以审阅的提纲。涉及外发时先问我。”

这个案例是本书虚构的教学场景，不是 Octop 自带的业务流程。它足够小，却跨过平台里最重要的边界：用户身份、Agent 工作区、附件、知识检索、模型工具调用、专家协作、人工审批和消息归档。我们用同一场景问系统：谁执行、读哪份状态、写到哪里、失败后还剩什么。

如果只看功能列表，这些能力像互不相干的插件。沿一次任务追下去，会看到 Octop 的主要工作是把可复用运行库接成一个能自托管的产品。

分析版本与证据等级#

本书依据 TencentCloud/Octop 提交 890111b7879665840414ca28ab168b05b0db0921，其 pyproject.toml 标记版本为 1.0.3b1。采集日期是 2026-10-27。网页中的源码链接固定到该提交，不随默认分支漂移。

全书区分三类表达：

表达 含义 怎样使用
源码事实 本次快照可定位的类、调用和检查 打开本章源码入口复核
架构分析 由组件关系推导的收益、约束和风险 当作有依据的解释，不当作实测
演进建议 面向更大负载的改造方向 先测量，不假设项目已实现

这次工作是静态架构研究，没有启动完整 Octop，没有调用真实模型、IM、Bridge 或 PostgreSQL 服务。书中提到测试文件，是说明仓库提供了相应的验证入口，不代表本次已运行并全部通过。

Octop 依赖独立发布的 octop-harness、octop-memory、octop-gateway 和 octop-browser。本书重点研究宿主如何使用它们，不把宿主的一段配置当成已审计外部库全部内部行为的证据。

先纠正三种阅读习惯#

第一，不以 README 的一棵树替代当前对象图。中文 README 仍有“按用户的 HarnessAgentManager”和“按 Agent 的 CronManager”的旧表达；架构文档与 server.py 显示的是进程级 AgentManager、Gateway 和 CronManager。正文采用当前源码结构。

第二，不从文件名推断协议。前端仍有叫 sseHelpers 的文件，普通聊天却已走双向 WebSocket；部分审批恢复仍用 SSE。迁移期间的旧命名不是传输协议的事实来源。

第三，不把“可选 PostgreSQL”理解成“平台完全无本地状态”。知识库索引仍有本地 SQLite sidecar；分段历史归档也有 SQLite-only 限制。选型必须按数据类别检查。

两条阅读路线#

第一次接触 Agent 平台，可按顺序读。先读需求与技术架构，再看身份、数据模型与工作区，随后沿一次请求进入工具与协作，最后讨论安全、界面与运维。已经维护相似项目，可以先读第八章的一次请求，再跳到第六章存储与第十一章团队，最后回读装配代码。

每章的练习都可以先在纸上推演。附带的标准库示例只演示身份、会话、审批和状态之间的关系，不模拟模型智能，也不是 Octop API 的替代实现。

阅读约定：图、示例与源码边界
