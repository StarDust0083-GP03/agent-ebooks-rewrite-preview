安全边界：能聊天不等于能管理

源码快照 2026-10-27 · 约 10 分钟

认证只回答第一个问题#

林岚已经登录，是否就能下载任意工作区文件、取消任意线程或调用任意工具？显然不能。认证解决“是谁”，资源授权解决“能操作哪个对象”，工具策略解决“这次动作是否允许”，执行环境解决“动作能触及哪里”。

JWT 中间件为 /api/ 路径设有明确豁免，并把已认证用户缓存到 request.state。WebSocket 路由还要自己处理相应认证，因为 HTTP 中间件的存在不自动等价为所有 WS 都被保护。

首次安装还有 setup_lockdown：没有用户时，非设置与健康等允许入口返回 setup_required。这与已经登录后的资源校验是不同阶段。

可见、可用、可写分开检查#

api/common/agent.py 的 require_agent_row 处理所有者、共享和管理员相关检查；require_agent_owner_row 再要求管理权。聊天订阅、取消与 resolve_thread_id 又校验 thread 的用户和 Agent。

沿这条调用链检查，比泛泛说“有 JWT 多用户隔离”更可靠。因为同一个专家可能被分享，单凭 agents.user_id 过滤无法描述所有合法访问；而允许访问共享专家也不该放开所有配置和私有线程。

用户组、角色、资源策略分布在 users 与 repos 中。架构书可以解释边界，但不能凭看到这些文件就给出“通过安全审计”的结论。

HITL 保存的是一项待决策动作#

危险工具需要人工审批时，运行图暂停。宿主把请求与用户、专家、线程、会话关联，生成 pending 标识；用户的批准或拒绝通过对应恢复路径传回运行时。

审批不是“模型问一句，你回答可以”。需要确认回答针对哪项动作、是否仍有效、是否属于当前主体、是否已经处理。项目有 HitlChannelCoordinator、pending store 与会话策略，用来协调 UI、CLI 和渠道差异。

运行时恢复与普通流式调用也需要线程级执行保护，避免同一等待点被并发恢复。本书未对所有审批竞态执行测试，因此这里描述的是机制与检查入口，不承诺所有工具端到端精确一次。

一条审批链的反例#

研究专家准备发送带附件的邮件，界面展示收件人 A；用户批准前，模型或另一路请求把待发送对象改成 B。如果批准仅绑定“发邮件”这个工具名，而没有绑定具体参数和等待点，批准 A 就可能被误用来发送 B。

验收应检查审批参数、pending_id、thread_id 和实际执行内容的一致性。工具参数修改后，是重新审批还是接受编辑，需要清楚契约。通用聊天文本不能成为任意工具的授权凭证。

已经执行的邮件也不会因之后取消 turn 而自动撤回。审批控制未来执行，取消结束计算，补偿处理既有副作用，三件事要分开。

Shell、文件、网络与秘密是不同面#

工具护栏管理命令规则；工作区与文件系统保护约束路径；Docker、OpenSandbox 或宿主隔离机制决定进程环境；ssrf_guard 等网络检查涉及请求目标；Fernet 相关代码用于凭证封装。

这些机制可以互补，不能互相替代。限制工作区路径不保证所有网络目标安全；加密数据库字段也不防止运行时日志泄漏。server.py 在普通日志级别降低 httpx/httpcore 输出，理由正是完整 URL 可能含 query secret。

实际部署应使用受信任插件、最小权限凭证和清晰的运行账号。自托管表示控制部署位置，不表示模型供应商、连接器或远程工具永远不接收数据。

Bridge 会扩大需要审视的信任面#

跨实例请求经过隧道进入专家所在侧。必须同时确认连接所有者、对端登录身份、可转发路径及最终资源权限。本地 user 7 和远端 user 7 不是同一个人，不能靠整数相等进行身份映射。

当前 tunnel_policy.py 有路径与方法约束。它比“通用 HTTP 隧道”这个协议能力更窄，且与前端远程能力清单可能不同。评审时应检查实际 allowlist，不按规划文档假定所有管理路径都允许或都禁止。

最小负面测试矩阵

用未登录、普通所有者、共享使用者、无权用户和管理员分别访问专家、线程、文件、取消、审批与管理接口。再加过期 pending、重复批准、路径穿越、内网 URL 和错误桥接身份。正向“能聊一句”不能替代这些负面用例。

动手检查#

工具配置写入“只读”，但插件在宿主进程中直接调用文件写接口。提示词和 JWT 能否阻止它？

答案提示： 不能据此保证。插件程序处于不同信任层，需检查实际执行权限、加载来源与策略落实位置。模型侧声明只读不等于宿主级沙箱。
