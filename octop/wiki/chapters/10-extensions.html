工具与扩展：Skill、Plugin、Connector 和 MCP

源码快照 2026-10-27 · 约 8 分钟

四种扩展不是四个同义词#

工作室想让专家按固定规范写稿，想加一个稿件状态面板，还想连腾讯文档。这三种需求不该都用“安装插件”笼统处理。

机制 主要解决什么 典型产物
Skill 给 Agent 可发现、可读取的操作知识 SKILL.md 与配套文件
Plugin 宿主/运行库可加载的程序扩展 工具、中间件、通道或 UI 协议载荷
Connector 把某用户的外部服务账户配置接成能力 凭证、实例配置、可用工具
MCP 一套工具发现和调用的互联协议 server 配置、工具 schema 与调用

技能可以指导模型调用工具，但不能代替服务端鉴权。MCP 能传递工具请求，也不会自动为每个工具赋予最小权限。

从用户配置到本轮工具#

装配时，AgentManager 从 ConnectorService 构造用户对应的 MCP 配置，结合内置、知识库、移动端和插件工具形成运行时能力。部分能力可以在当轮选择中继续收窄。

需要区分三个集合：系统安装了什么、这位用户授权了什么、这位专家这一轮可用什么。如果插件已安装但未启用，不应仅因它出现在磁盘上就进入每个专家的工具列表。

PluginManager 启动时播种 bundled 插件并加载已安装插件。官方架构文档指出 bundled 默认关闭。插件代码在宿主边界执行，其风险不能与“读取一段技能文本”混为一谈。

Connector 模式决定实际调用位置#

catalog.json 是内置连接器元数据源。不同模式有不同路径：

  • remote：运行库连接供应商 MCP 地址。
  • gateway：使用进程内 Python 适配器，配置中可能只是名称占位。
  • internal：Octop 托管 /api/internal/mcp，运行库通过 HTTP 加载。
  • 目录中也有 stdio 类型接入，应按相应配置和调用器理解。

同样叫“连接器”，有的走网络，有的进程内执行，还有的启动子进程。超时、日志、凭证传播和资源释放因而不同。新增服务时应先确定调用位置，再设计配置页面。

大型 UI 载荷为什么要离开模型上下文#

插件可能返回适合界面渲染的 octop_ui 内容。让模型反复看到一份大型 UI 数据会浪费上下文；只保留一个空壳又会让界面无法显示。

OctopUiOffloadMiddleware 的任务就是处理这类 envelope，使模型侧和 UI 侧按各自需要消费。它的作用范围是特定插件载荷，不是任意工具结果的通用对象存储方案。相关文档独立说明协议，避免前端、工具和中间件各猜一套字段。

这是一个典型产品化问题：运行库只要能返回工具结果，产品还必须考虑结果的体积、展示与后续上下文预算。

一次外部写操作需要几道门#

假设模型准备把提纲写进腾讯文档。至少需要确认当前用户的连接器实例有效，工具在当前专家上启用，参数符合 schema，工具策略允许或触发审批，真正调用供应商后得到可核验结果。

供应商请求超时尤其危险：可能从未写入，也可能已写入但返回丢了。模型重试不是业务幂等。若工具支持幂等键、查询已创建文档或可对账操作记录，应在工具边界使用，不能让模型“再试一下”承担去重职责。

这与 SAM 系列回调幂等的讲解思路相通：先找重复从哪里来，再为具体动作选稳定标识。它不意味着 Octop 已内置支付式三层幂等，或每个 MCP server 都支持同一保证。

新增连接器时的最小检查表

核对凭证属于谁、如何加密、授权可否撤销、工具命名是否冲突、schema 是否兼容、读写是否区分、超时能否判定结果、日志是否含秘密。探测成功只证明一条接入路径可用，不证明所有业务动作安全。

动手检查#

一份 Skill 写着“只有管理员可以外发”。普通用户能否因此被服务端可靠阻止调用发送工具？

答案提示： 不能。模型提示是行为指导，不是服务端授权。必须在工具调用边界根据认证主体与策略校验，必要时进入 HITL；不能把用户可修改的文本当安全策略源。
