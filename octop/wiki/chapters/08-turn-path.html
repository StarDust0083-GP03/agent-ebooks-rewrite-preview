第 08 章

一次对话：从 WebSocket 到模型再回来

源码快照 2026-10-27 · 约 10 分钟

先把入口和执行者分开#

前面已经有用户、专家、线程和存储，现在追一次真实入口。林岚点击发送后，浏览器连接 /api/agents/{agent_id}/chat/ws。这个连接负责接收 user_turn、订阅、取消与控制消息，不直接承担全部模型循环。

服务端先解析 token、检查专家访问，再注册连接。用户提交的消息经过结构校验和 prepare_dashboard_turn，解析线程、模型选择、MCP、Skill 与附件。接着生成 InboundMessage，交给 ChannelManager 排队。

这里是进程内消息调度，不是引入了 Redis 或外部 MQ。ADR 001 的“无外部队列”与内部 enqueue 不矛盾。

请求被翻译成共同语言#

Web 表单与 IM 消息形态不同。统一的 InboundMessage 把差异收敛到内容、主体、通道、tenant_id 和 metadata。此路径中 tenant_id 用来选 Agent，不应直接理解为拥有完整 SaaS 语义的租户隔离层。

GlobalProcessor.iter_turn_chunks 为使用原生 chunk 的入口处理请求；IM 路径则还会经 project_stream 转成 MessageEvent。模型不需要自己理解飞书消息格式或浏览器组件状态。

user_turn
 → 校验用户、专家、线程、附件
 → InboundMessage
 → ChannelManager.enqueue
 → GlobalProcessor
 → AgentManager.stream
 → HarnessAgentManager.stream
 → 模型及工具循环
 → chunk 记录、补充、投递

这是控制流。存储提交、工具执行和网络发送不共享一个大事务。

一个关键顺序：先订阅，再让出控制权#

ws.py 有一段容易被当成细节的逻辑：线程确定后，先 hub.subscribe，再等待 steer 接纳或其他后续处理。因为 await 会把执行权交出去，另一个运行中的 turn 可能马上产生消息。

如果先 await 再订阅，消息可能已经向房间推送，而此连接尚未加入，最初几帧就丢了。这个问题和模型速度无关，是异步调度的时序问题。

接下来再判断本轮是否作为 steer 进入正在运行的任务，或者作为新 InboundMessage 入队。不是每次用户追加文字都一定启动一个全新独立模型循环。

主处理器在模型前后做什么#

普通请求进入运行时之前，要处理 slash、HITL 待答、线程绑定、模型和能力配置。并不是所有输入都会到 LLM；如某个管理命令已由宿主解释，就可以直接产生响应。

运行过程中，宿主跟踪 usage、历史与轨迹。以下是当前源码中的关键顺序摘录：

usage_tracker.observe(chunk)
history_tracker.observe(chunk)
await flush_tracker(history_tracker)

这几行之后还有轨迹记录、HITL 注册、工具结果增强和对外 yield。flush_tracker 是否形成具体提交，取决于选中的 tracker 与历史格式，不能把这三行解释成所有模式都具有相同持久化保证。v2 的提交先于发送约束见存储章。

工具结果还可能关联工作区产物并转换成附件帧，且做去重。否则一次重放的工具结果可能让界面反复出现同一个下载文件。

断线与取消是两件事#

本地聊天路径的 finally 注释明确：连接断开不应取消在途 turn。服务端注销连接，任务仍可继续。浏览器回来可以重新订阅，继续接收后续帧。

这叫弱流式恢复，不等于从任意帧号完整重放断线期间每一个 token。缺口要依赖历史读取与状态协调弥补，不能只凭“WS 重连成功”宣布无损。

显式 cancel 则校验线程后，标记 steer 取消、丢弃待接纳内容并向 Agent 注册表发取消信号。取消是请求，不是外部副作用的回滚：已经发出的邮件、已经写出的文件不因停止流式回答而自动撤销。

模型失败不应变成一条成功回答#

processor 使用 stream_ok、异常记录和 finally 清理区分完成与未完成。失败时产生 error 并保存不完整回合，而不是只把错误文案当作普通 AI 答案混过去。

模型 failover 也有边界：SafeModelFailoverMiddleware 只在自动路由及适合的失败类型下尝试候选，同时检查多模态需要、健康状态和上下文容量。它不是“任何异常都换模型再执行整个任务”。

排查一次“没收到回复”

依次问：WS 是否认证通过？线程是否正确订阅？消息是否入队？处理器是否启动？模型是否返回 chunk？历史写入是否成功？投递到哪个 thread？前端是否拒绝了错误线程的帧？每个问题对应不同文件，不要从 UI 没字直接跳到更换模型。

动手检查#

林岚在生成过程中关掉页面。过一分钟回来，历史显示最终提纲。能据此证明浏览器离线时所有 token 都逐个重放了吗？

答案提示： 不能。它只证明最终可读结果可能已持久化并被重新获取。服务端继续执行、后续订阅和历史补齐是三件事，逐帧重放需要额外的序号、保留和确认协议。
