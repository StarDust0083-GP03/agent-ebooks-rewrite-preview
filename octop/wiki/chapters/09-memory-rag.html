第 09 章

记忆与知识库：两条不同的检索路径

源码快照 2026-10-27 · 约 8 分钟

昨天的约定与今天的资料#

林岚说过“优先给中文资料”，这可能适合成为 Agent 的长期记忆。上传的出版规范则是一份有版本和来源的文档，适合进入知识库。两者都影响回答，但保存的单位、权限范围和更新方式不同。

聊天历史记录这次说过什么；checkpoint 支撑图的状态；Memory 组织可复用信息；知识库索引文档证据。它们都可能存文本，不意味着可以合并成一张“聊天信息表”。

Memory 后端由宿主解析#

memory_backend_from_agent_config 读取 Agent 配置。没有显式指定后端时，SQLite 控制面保留运行库的默认；PostgreSQL 控制面则默认向 Memory 传同一 DSN，并按 Agent 命名空间区分。显式 sqlite 覆盖仍然存在。

这是存储选择，不是授权策略。让多个专家复用一个 DSN，并不等于它们共享记忆；反过来，分开文件也不能代替应用层访问控制。

源码还给记忆辅助抽取模型做解析与兼容处理。日常聊天用的默认模型和记忆维护模型可能不同。因此“聊天正常、记忆提炼失败”并不矛盾，应检查各自模型配置及可用性。

本书不展开外部 octop-memory 的全部提取与召回算法，避免把宿主参数名字当成内部算法证明。

知识库索引没有依赖大型向量服务#

KnowledgeIndex 的类注释很直接：每个知识库使用一个本地 SQLite sidecar。chunks 表保存 chunk_id、doc_id、ordinal、text、embedding 和 metadata；embedding 以二进制形式保存。

replace_doc_chunks 在事务中先删除该文档旧片段，再写入新的片段。它处理的是单个索引内的文档替换，不保证“上传源文件、解析状态、embedding 服务、索引内容”跨组件原子提交。

search 在进程中计算余弦相似度。这样的实现部署简单，但不能根据“支持向量检索”四个字就假设已经用了 ANN 索引或独立向量数据库。数据增长时应测量扫描量、向量维度、内存与延迟。

检索先限制集合，再排序#

retrieve_context 的读取流程可以概括为：

检查知识能力与 query
 → 为 query 生成 embedding
 → 取得当前主体可见知识库
 → 与本轮选中的知识库取交集
 → 在 ready 文档范围内筛选命中
 → 汇总并按 score 排序
 → 截取 k 个候选
 → 在字符预算内拼接上下文与引用

当前默认 k 为 8，正文字符预算为 6000。这是快照中的实现常量，不是所有模型的通用最佳参数，也不是 token 预算。中文、英文与代码的字符到 token 比例不同。

权限应在候选集合形成之前起作用，不能先搜出别人材料，再指望提示词让模型别引用。ready 文档限制则避免把未成功完成索引的材料误当可用证据。

一个可见的降级点#

retrieve_context 把同步检索放到 executor，外层捕获失败后记日志并返回空字符串。收益是知识检索失败不必让整个聊天崩溃；代价是用户可能收到没有私有证据支持的普通回答。

对工作室的出版规范查询，这个降级是否可接受取决于产品约束。如果要求“只能按上传规范回答”，检索不可用时应显式提示而不是静默继续。这是演进建议，不代表当前所有入口已实现严格失败关闭。

引用标记也只说明来源关联，不自动保证答案完全受引用支持。验收应检查最终模型输入、选中的片段和实际回答，而不只看界面有没有一个引用徽标。

一个有用的对照实验

准备两份虚构规范，分别可被林岚和周越读取。让两人提出相同关键词。记录可见集合、命中片段、注入正文及回答引用。这样能区分授权错误、召回错误、注入缺失和生成错误；只测“模型答得像不像”无法定位问题。

动手检查#

控制面切到 PostgreSQL 后，本地 knowledge 目录能不能直接删除，等系统从 PG 里自动恢复全部向量？

答案提示： 不能这样推断。知识索引在该快照里是本地 sidecar，需检查原始文档与索引重建路径。控制面远程化没有自动迁走所有数据。
