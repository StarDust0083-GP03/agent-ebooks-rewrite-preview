第 05 章

身份与会话：四种 ID，四条边界

源码快照 2026-10-27 · 约 8 分钟

一位用户可以使用别人的专家#

前面的配置装配解决“专家有哪些能力”，还没有解决“当前请求属于谁”。Octop 至少要区分 user_id、agent_id、session_key 和 thread_id。把四者合成一个字符串会让权限和生命周期互相干扰。

标识 回答的问题 典型变化
user_id 当前主体是谁 登录用户改变
agent_id 使用哪位专家 切换专家
session_key 哪个入口会话绑定当前线程 Web、CLI、IM 来源改变
thread_id 哪份持续对话与图状态 新建、切换或分叉线程

Agent 归属是资源关系，thread 归属是对话关系。林岚分享了研究专家，周越可以使用它，但不应因此获得林岚的私有 thread。

先授权专家，再授权线程#

api/common/agent.py 将访问与管理分开。所有者、管理员和满足分享范围的用户可以获得不同访问能力；修改专家配置则有 owner 级检查。用户组分享还会进入 expert_visible_to 等可见性逻辑。

聊天准备阶段会再次校验指定线程。以下是 resolve_thread_id 中的核心判断，省略了后续绑定操作：

row = thread_registry.get_thread(thread_id)
if row is None or row.agent_id != agent_id:
    raise OctopError(ErrorCode.AGENT_NOT_FOUND, ...)
if row.user_id != user_id:
    raise OctopError(ErrorCode.FORBIDDEN, "thread not owned by user")

这里省略号是教学摘录标记，不是可运行代码。第一关防止给 A 专家塞入 B 专家的线程，第二关防止同一共享专家下读取别人的私人线程。只验证 JWT 或只检查 agent_id 都不够。

session_key 是入口绑定，不是授权凭证#

Web 默认会话键可表示为：

<agent_id>:dashboard:<user_id>:dm

CLI 与 IM 有各自的键规则。IM 会把平台会话及私聊/群聊语义纳入区分。thread_id 本身不负责编码来源，来源信息可以单独存入线程记录。

为什么不直接拿 session_key 当 thread_id？因为同一个入口可以切换到新线程，旧线程仍需保留。绑定可变，对话身份稳定。ThreadRegistry 因而负责创建、绑定、归档等关系，而不只是提供一个随机 ID。

任何由客户端带来的 session_key 都只能当作待验证的路由输入，不能因为字符串里包含某个用户编号就当作服务端已证明身份。本书并未穷尽审计所有调用者，这是一条需要持续测试的安全不变量。

用一组具体 ID 走一次#

教学例子里，林岚为 user 7，周越为 user 9，研究专家为 research。两人各自使用：

research:dashboard:7:dm → thread-L
research:dashboard:9:dm → thread-Z

专家共享以后，两条映射仍应独立。林岚新建会话时，自己的入口可改绑 thread-L2；thread-L 作为旧对话保留。周越复制 thread-L 的 ID 发起订阅，服务端应拒绝，而不是因为两人选中同一专家就放行。

再加一个 IM 群聊，它是新的入口语义。要不要和 Web 共用对话，不应靠碰巧相同的字符串决定，需要明确的绑定规则和授权。

资源删除也必须沿标识追踪#

删除专家可能涉及线程、checkpoint、记忆、工作区和正在执行的调用。删除一条线程则不等于删除专家的全部长期记忆。manager.py 的线程清理与回收逻辑提示，这些动作已经不是简单的一条 DELETE。

制定数据删除需求时，要列出每种数据归属。否则界面里删除了会话，用户可能以为历史、工具产物、派生记忆和备份都消失了，实际只移除了一个视图对象。

如何把权限规则变成测试

准备同一所有者、共享用户、未授权用户和管理员四个主体。分别测试专家读取、配置写入、线程读取、WS 订阅与取消。共享用户“可聊天、不可改配置、不可读别人的 thread”必须是三条独立断言。

动手检查#

周越没有专家所有权，但有分享访问权限。为什么允许他创建自己的对话，却不允许他改这个专家的模型？

答案提示： 运行能力的使用权与资源配置权分开。模型和工具改变会影响专家所有者及其他使用者；聊天则可通过独立线程控制范围。不能把“能访问资源”的布尔值复用成全部管理许可。
