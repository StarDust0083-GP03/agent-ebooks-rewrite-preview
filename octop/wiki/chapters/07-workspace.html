第 07 章

工作区后端：远程文件不等于远程执行

源码快照 2026-10-27 · 约 8 分钟

附件不是一条预览 URL#

林岚上传访谈时，浏览器可能获得一个预览链接和一个工作区路径。后续聊天准备会优先根据 workspace_path 形成附件内容；只带预览 URL 的块不能等价为已经入库、可被工具读取的附件。

这背后的问题是权威位置。浏览器看得到一个地址，不说明模型工具能读取它，也不说明它属于当前专家。先落到受控 inbound，再传递工作区引用，才能让输入、读取与权限检查对齐。

BackendWorkspace 隔离的是内容访问#

Octop 支持本地文件系统、对象存储、PostgreSQL 文件后端，以及 Docker、OpenSandbox 等后端形式。adapter.py 将控制面后端行转换为 harness 的 backend spec；resolver 再结合 Agent 配置选择实际后端。

这不表示这些后端都有完全相同的执行与文件语义。把文件存进 S3 解决的是存取位置；在 Docker 中执行命令涉及进程、挂载与权限。它们可能出现在同一配置体系，仍必须分别分析。

项目的 agent-backend-file-io 文档要求 Agent 内容文件通过工作区接口访问，而不是直接 Path.read_text。假如编辑专家改用 COS，而 API 仍直接读本机同名 SOUL.md，就会出现“页面说已修改，实际模型读旧内容”的分叉。

两类路径必须区分#

内容路径：SOUL.md、skills/、inbound/、生成文件
    → 走 BackendWorkspace 的内容访问

本地运行材料：部分 checkpoint、harness 管理的状态与回退文件
    → 按运行库及所选后端的具体约定处理

docs/architecture.md 描述了本地运行文件的默认安排；ADR 002 又说明 PostgreSQL memory 场景可复用相关 checkpoint 存储。两者需要组合阅读，不能得出“checkpoint 永远是本地文件”这种绝对结论。

本地 workspace_dir 有时仍承担运行锚点，即使某些内容已搬到远程后端。看到本地目录存在，不说明所有内容都以本地副本为权威。

用一次提示文件修改看差异#

教学流程是：界面提交新的专家准则，服务端验证专家配置权限，取得该专家的工作区接口，写入准则文件，再根据能力选择同步或重载。

错误实现是直接拼接本地路径并写入。它在默认 filesystem 下看似正常，换到远程后端才暴露。另一个错误是先对前端返回“保存成功”，把实际后端写入留给无人跟踪的后台任务。

远程后端失败需要成为可见结果。否则林岚会以为专家已经改为“外发前审批”，实际执行仍使用旧规则。这已经从存储问题变成安全预期问题。

后端替换需要契约测试#

新增后端时至少核对文本和二进制、目录列举、相对路径、覆盖写、缺失文件、路径越界、下载和失败传播。对象存储没有天然 POSIX rename 语义；远程延迟也会改变读取大量小文件的代价。

执行能力还要单列：shell 在哪里运行？浏览器是谁的进程？工作区文件如何进入沙箱？网络请求是否受同样约束？不要用“支持 Docker 后端”代替对所有工具执行环境的检查。

这些是接入验收建议，不代表本书对每一种后端执行了兼容性测试。

与 SAM 工程分层的一个对照

支付系列把渠道差异留在渠道适配层，避免编排层直接面对每家接口。工作区后端也有相似的边界价值：上层提出读写内容的需求，不应到处重写 COS、S3 或本地路径细节。相似的是隔离差异的方法，不是要求照搬 Java 的模块结构。

动手检查#

一段新代码用 Path(workspace_dir) / "inbound" 找附件，本地测试通过。为什么仍不能认为符合后端抽象？

答案提示： 它绕过内容后端，隐含附件必在本机该路径。应查看调用者需要的是后端内容引用，还是已按契约材料化的本地临时文件；只有后者才可按明确生命周期使用本地路径。
