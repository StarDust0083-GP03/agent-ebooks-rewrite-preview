第 02 章

总体架构：单进程，不是单模块

源码快照 2026-10-27 · 约 8 分钟

Octop 首先是一个宿主#

林岚看到的是聊天界面，维护者看到的却是一组持续运行的组件：认证、Agent 注册表、IM 连接、定时任务、消息订阅和数据库。Octop 把它们装进同一个 Python 服务，而不是要求用户先部署消息队列、worker 与独立控制台后端。

把它归类为“模块化单体”比“聊天机器人”更准确。这是架构分析：它具有多种领域能力和明确的库边界，但核心运行时由一个进程持有。单进程减少部署部件，不会自动减少模块之间的复杂度。

四个产品边界#

对外表面包含 Dashboard、Click CLI 和 HTTP/WS API。API 层处理认证、参数、状态码和传输，不应该自行拼装一套与 IM 不同的模型循环。

宿主业务层位于 infra。这里的 AgentManager 是进程级注册与装配入口；Gateway 连接渠道、线程与消息；CronManager 管理调度；SharedServices 提供仓储与公共服务。文件夹名叫 infra，但其职责不只是数据库驱动，还包括相当多产品逻辑，不能机械套进“纯基础设施层”。

可复用库承担不同任务。octop-harness 提供 Agent 运行时与工具编排；octop-gateway 提供通道协议；octop-memory 提供记忆能力；octop-browser 提供浏览器相关能力。依赖名可以从 pyproject.toml 核实。详细内部算法需要另读相应库，不能从宿主的 import 推演出全部实现。

存储层也不是一个部件。控制面记录用户和配置；运行时 checkpoint 保存图状态；工作区承载内容文件；历史与知识索引还有自己的保存形式。这些边界到存储与历史一章再展开。

为什么不先拆服务#

ADR 001 给出的背景是自托管用户：安装一个包，初始化，再启动服务。把 Redis、Celery 或单独 worker 设为必需，会把一个人的安装问题变成多服务运维问题。

Agent 请求经常等待模型、网络或工具返回，异步 I/O 可以在等待期间处理其他请求。这支持单进程选择，但不说明 CPU 密集型 PDF/OCR、向量扫描或同步数据库调用没有成本。事件循环里出现阻塞，仍会影响整个实例。

另一个好处是对象间可以直接传引用。CronManager 可以得到 Gateway，AgentManager 可以得到仓储与策略，无须再设计远程接口。代价也来自同一点：这些对象、锁和订阅只存在于本进程，多开实例不会自动共享。

PostgreSQL 没有改变进程模型#

ADR 002 引入可选 PostgreSQL 控制面。它改变的是持久化位置和驱动，不是给所有内存组件提供分布式一致性。文档明确不承诺多实例同时写。

例如运行两个进程读取同一个 cron 表，每个进程都可能恢复自己的调度器。数据库里只有一条任务，不代表实际只有一个调度所有者。要做横向扩展，需要任务认领、租约、幂等和消息路由，而不只是换连接串。

动手检查#

工作室有 12 位编辑，打算把数据库换成 PostgreSQL，再启动三个相同服务以提高并发。指出两种不能仅靠数据库解决的状态。

答案提示： WebSocket 订阅与正在运行的 turn、Cron 调度器、团队在途派工和取消信号都带进程内状态。要先设计所有者与路由；“12 人”本身也不足以证明需要拆分，应测量同时活跃任务及尾延迟。
