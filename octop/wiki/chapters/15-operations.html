部署与验证：把恢复当成一项功能

源码快照 2026-10-27 · 约 10 分钟

一个核心服务，不等于没有其他进程#

Octop 的单进程模型描述的是核心宿主。模型服务可以在外部，工具可以拉起子进程，浏览器有自己的进程，Docker 后端也有执行环境。不要把“单进程”写成操作系统里永远只有一个 PID。

wheel 可以带构建后的 Dashboard；开发时 Vite 与 Python 分开运行，发布时静态资源进入 src/octop/dashboard。Docker 则把这些内容和运行环境一起打包，数据目录仍要持久挂载。

desktop/README.md 明确当前桌面壳为 Wails v3，加载打包的 portable runtime，启动 Octop。它与 infra/control/desktop 远程桌面流不是一个模块；仓库残留 Electron 说明也不是当前桌面壳技术栈的证据。

定时任务为何也是主链路的一部分#

CronManager 是进程级 APScheduler 管理器，从数据库记录恢复任务。CronJob 把任务交给 CronDeliveryService，并记录运行状态、审计与指标。

task_type 区分直接推文本和运行 Agent 后投递。两者的成本、失败点与权限需求不同。林岚每天收到固定提醒，不一定要花一次模型调用；每天基于新资料生成简报，才需要实际 Agent 处理。

cron 的运行状态 ok 至少表示当前投递流程按其契约成功返回，不自动表示每个外部收件人已经阅读，也不构成所有下游副作用的事务证明。

多进程恢复相同任务时的所有权问题，在这里比“有没有换成 PG”更关键。

备份必须匹配真实数据布局#

基础清单应包含配置、主库、秘密材料、Agent 工作区、checkpoint、Memory、知识文件与索引，以及启用时的历史归档和标记。秘密材料要按其恢复依赖安全保存，不能把它们随便打进公开样例。

SQLite 运行中的一致快照不等于复制一个正在写的文件；PostgreSQL 有自己的 pg_dump 路径。ADR 002 不承诺跨引擎恢复。history_v2 的多库协调与路径身份限制则需要额外遵守。

“能导出一份聊天 JSON”和“灾后能恢复整个服务”是两个验收项目。前者帮助核对记录，后者还需要身份、配置、图状态、文件与依赖版本匹配。

按风险层次读测试#

测试层 可以验证 不能单独证明
纯逻辑单测 路由、标识、状态合并、参数规则 真实模型与外部服务
API 集成测试 认证、资源边界、WS 与服务生命周期 全部部署环境
PostgreSQL 专项 迁移、仓储、checkpoint 等兼容路径 不依赖本地 sidecar
live 测试 特定凭证与供应商的真实交互 所有供应商与所有权限
恢复演练 指定故障点下的恢复结果 未测试故障和硬件损坏

仓库有 unit 与 integration，并用 marker 控制 live、slow、postgresql 等范围。缺凭证的测试可能跳过。CI 绿灯因此要结合实际执行矩阵理解，不应写成所有真实服务都已验收。

本次只对电子书构建与配套教学模型运行检查，没有运行 Octop 自身测试。

用六次故障推演替代一句“支持高可用”#

在隔离测试副本中依次验证：

  1. 模型在工具调用前失败，历史和 UI 如何结束。
  2. 工具动作成功但返回超时，重试是否重复副作用。
  3. 客户端断线后重连，后续帧和历史是否一致。
  4. 审批暂停时退出，再启动后待处理动作是否可识别。
  5. 写入历史时磁盘满，是否仍向用户宣称成功。
  6. 从完整备份恢复，线程、附件、记忆和配置是否能关联。

这套清单没有预设系统应通过所有项目，而是要求把实际结果写下来。有的能力当前不支持，明确限制比伪装成自动恢复更安全。

上线前先保住哪个指标

先量事件循环延迟、活跃 turn、模型与工具耗时、历史提交延迟、数据库锁等待、重连次数与失败率。注册用户数不能代表同时执行压力，模型 token 速率也不能替代整体请求尾延迟。

动手检查#

工作室每晚备份 octop.db，其他目录不备份。某天服务器故障，恢复后用户和专家列表还在，但附件和记忆缺失。这能算备份成功吗？

答案提示： 只能说部分控制面恢复了，业务恢复目标未满足。应先按数据类别定义 RPO/RTO 与恢复验收，再制定完整备份方案；不能用主库文件存在代替可用性检查。
