多 Agent：房间共享，状态分离

源码快照 2026-10-27 · 约 8 分钟

把合作拆成编排与执行#

现在让研究专家整理背景，法务专家核查风险，主持人汇总结果。若只把三个人的消息拼在同一份上下文里，谁负责工具、记忆与取消会很快混乱。

Octop 的团队主持人是 agents.kind=team 的特殊专家，成员仍是独立专家，可以参与多个团队。团队编制在主持人工作区的 .octop/manifest.json 中，数据库 kind 用于索引。这里没有一张被本书假想出来的独立成员主表。

普通专家和团队主持人使用同一个 Agent 生命周期体系，但工具权限与调用模式不同。主持人主要协调，不承担完整文件、浏览器和 MCP 执行能力。

一个房间，三份执行状态#

房间 conversation_id = 主持人 thread_id
  主持人 checkpoint：conversation_id
  研究成员 checkpoint：conversation_id~research
  法务成员 checkpoint：conversation_id~legal

各专家 → 各自工作区 / 记忆
成员流 → 房间转播，带说话人标记

用户看见同一条时间线，不表示多个 Agent 写同一个 checkpoint。展示共享与状态共享是两回事。

成员得到的是主持人改写后的任务说明，群聊历史作为背景；团队准则与记忆在主持人侧，派工时需要明确交付。模型不能因为“加入团队”就自动读取所有同事的私有工作区。

派工、回叫与收尾#

当前专家团队文档描述：普通专家侧以同步互问为主；主持人异步派工后立即返回，成员完成后由平台回叫主持人。成员能同步询问同事，但不再异步往群里拉人。

异步调用需要保留 source_agent_id、source_thread_id、目标与任务标识，才能把后续结果送回发起位置。否则成员几分钟后完成时，平台不知道回到哪个房间，也不知道还应不应该唤醒主持人。

当前文档说明 inbox 按 callee 协调，同一成员串行、不同成员可并行，主持人回叫按源 thread 串行。早期 mailbox 方案写过单 worker 串行，不能把旧方案当当前宿主契约。具体库内调度器仍需在固定 octop-harness 版本中独立复核。

为什么要按 job_id 幂等记账#

团队有在途派工时，不允许随意移除成员或删除对应专家。TeamJobTracker 为这项约束记录 busy 状态。

下面是 begin 的真实核心片段：

if job_id:
    if job_id in self._jobs:
        return
    self._jobs[job_id] = key
    return

同一个 job 重复通知开始，不应把繁忙计数加两次。结束时按 job_id 移除，也比“每条结束事件都减一”更稳定。这里幂等的是在途记账，不是成员执行的全部外部副作用。

TeamJobTracker 使用进程内 dict 和 Lock，重启丢失，源码注释明确它不能为重启前残留任务提供 fencing。不能据此宣称有持久任务队列或跨进程安全。

点停止，究竟停止了谁#

团队文档明确：Dashboard 取消只取消主持人当前 stream；已排队或正在运行的成员不因此取消。成员仍可能完成并回叫。

对林岚来说，这可能表现为“我明明停止了，研究专家还在回话”。它不必然是实现错误，而可能是当前取消语义。界面与文档应清晰表达停止本轮和停止整组任务的差别。

如果工作室要求“一键取消全部，并阻止后续外发”，就需要扩展任务树取消、回调抑制与工具边界检查。只在前端忽略成员消息，不会停止实际工作。

团队与子 Agent 也不要混淆#

本仓库既有 subagent 目录，也有完整专家团队。一个运行时里的子任务，与拥有独立身份、工作区、分享和会话的专家成员，生命周期不完全相同。

选哪一种应看需要共享什么、隔离什么、结果回到哪里，而不是看“多 Agent”标签是否相同。能用一个临时子任务解决的处理，不一定需要创建一位长期专家。

把支付回调的阅读方法用在团队协作

SAM 编排章节会追踪“哪个子结果到了，什么时候合并”。阅读团队也可以这样做：谁派工、谁收结果、哪个 job 已结束、由谁判断收工。但团队总结不是资金事务，不要套用全成功或全回滚的承诺。

动手检查#

主持人停止后，研究专家创建了文件并回叫。为了做到“界面上看起来已停止”，直接丢弃所有后续帧是否足够？

答案提示： 不足。只是隐藏信息，既没取消工具，也没协调历史和任务状态。应先定义取消的范围与已发生动作的处理方式，再决定哪些回调可以继续、哪些必须标记取消。
